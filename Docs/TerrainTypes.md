# Terrain types

Plan for 16 ground layers per area instead of 8, and for the next ground materials after grass, weeds, sand, mud, gravel, stone and water: dirt, dry grass, a flower meadow, tall grass, wooden planks, plaza tiles, shallow water, an ocean, lava, snow, ice and raised ground. [TerrainBlending.md](TerrainBlending.md) is the renderer they are drawn with and the phases that built it; [Architecture.md](Architecture.md) describes what exists. This file describes what to add and in which order.

Every rule in [Multiplayer.md](Multiplayer.md#rules-for-new-code-starting-now) applies. Ground is scene content every machine loads the same way, so a new material is drawn locally with nothing replicated. A terrain that changes gameplay (damage, slipping) does so on the server, through the systems that already own that gameplay.

## Where we start

The state before Phase 1; its notes say what changed.

- An area's ground is up to 8 layers: a control map stores each cell's layers as the bits of one byte (`TerrainControlMap`, an `R8` texture, `MaxLayers` 8), and the shader's per-pixel arrays are sized for 8 (`TB_MAX_LAYERS`). Every generator, every area and the area template list the same 7: grass, weeds, sand, mud, gravel, stone and water, in that draw order, which is also the navigation priority.
- The 8 is enforced in `TerrainControlMap.Build`, the renderer's build checks, `AreaGroundSetup` (the writer and Convert Ground refuse more, and drop drawn layers past 8 with a warning), and assumed by the debug view's colours (`TBDebugColour`: 7 pure colours and orange) and `TerrainBlendProbe`'s blob checks (`DebugLayers` 8). `AreaTerrain`'s runtime edits already index up to 256 layers.
- A material is a `TerrainMaterial` asset with textures written by its recipe (`TerrainMaterialRecipe` subclasses), a plain tile, a palette and a `TerrainType2D`, plus rules in `TerrainMovement_Default` when it is not walked like grass.
- What a material can already do in the shader: chips and stones from a cell field (gravel, stone), glints and sparkles (water), a swelling rim (water), sinking with a bank (water), swaying weeds (weeds), and a seamless edge over a material of the same look (weeds over grass).
- Generators: the Clearing, the Village Forest and the Lakeside (see [SceneGeneration.md](SceneGeneration.md)).

## Goals

- Up to 16 ground layers in one area, with the shader, the debug view, the probe, the brush preview and every check following.
- Every terrain listed above, paintable in any area that lists it, each with its own look, edge rules and movement.
- No area pays for layers it does not use: the per-pixel cost and the texture memory follow the layers an area lists, not the maximum.
- Shader features stay general: each new effect is a material setting another material can reuse, not a special case for one material.
- Every terrain a generator can lay is laid by at least one generator, and every terrain is covered by tests like the existing ones (recipe, lookup texture, generator layouts).

## Non-goals (for now)

- Footprints, tracks or any ground that changes while playing (snow you walk into, lava that spreads). Ground stays static scene content.
- Real elevation for gameplay: raised ground is a look, and its edges block movement only where walls would.
- Weather and seasons that switch materials at runtime.
- Water that flows. Shallows and the ocean animate inside a fixed shape, like the pond.

## Decisions

- **16 layers, from a 16-bit control map.** The control map moves from `R8` to `R16` (one 16-bit channel; each texel's value is the cell's layer bits, read in the shader as `round(r * 65535)`), its cells from bytes to `ushort`s, and `MaxLayers` and `TB_MAX_LAYERS` to 16. `R16` is supported for sampling on the platforms we build for (Windows, D3D11/12 and Vulkan); the renderer checks `SystemInfo.IsFormatSupported` for sampling and fails loudly otherwise, and `RG8` (low and high bytes in two channels) is the fallback if a target lacks it. Check the format against Unity's docs before building it.
- **The cost follows the layers an area lists.** The shader's loops already stop at the area's layer count (`ins.layers`), so an area of 7 layers does the same work under a 16-layer shader as today; only the arrays (distances, pair weights, shapes) grow, which raises register use. The lookup texture grows with the layers (1 + L + L(L + 1) rows: 57 for 7, 289 for 16) and the albedo, cell field and height arrays get a slice per layer, so 16 layers at 512 px is about 48 MB on the GPU against 19 MB for 7 today. Measure a 16-layer area against a 7-layer one before calling the phase done. Phase 1 found the arrays did matter and removed them from the per-pixel work; a pixel now pays only for the layers filled around it (see Phase 1's notes).
- **Per-area layer sets, before the project passes 16 materials.** The planned materials add up to 18 layers, more than one area can hold even at 16. Each generator will list only the layers its area uses, in the shared order, which also keeps memory and register use down. The renderer already draws whatever list a grid gives it, so this is generator, writer, template and test work; it must land before the 17th material (the ocean, Phase 8).
- **One shared draw order.** Layers keep a project-wide order, so a pair looks the same in every area and pair overrides keep their meaning: each area's list is a subsequence of it. The order, bottom first: grass, dry grass, meadow, weeds, tall grass, snow, dirt, sand, mud, ice, gravel, plaza, stone, shallows, water, ocean, lava, planks. Raised ground is not a layer (see Phase 10).
- **The shared order is a list on `TerrainStyle`**, `layerOrder` (decided in Phase 2), not a separate `TerrainLayerOrder` asset. The order exists so that a pair is always the same upper material over the same lower one, which is exactly what the style's pair overrides are keyed on, so the order and the overrides describe one thing, the edges between materials, and change together. Every generator and every area's renderer already names its style, so the writer, Convert Ground, the brush and the tests reach the order with no new reference, asset lookup or service. The cost: a second style would carry an order of its own. If the project ever has several styles, move the list to an asset they share. The list holds only the materials that exist (seven until Phase 3: grass, weeds, sand, mud, gravel, stone, water; ten since: grass, dry grass, weeds, dirt, sand, mud, gravel, plaza, stone, water); a new material goes in at its place from the full order above.
- **Planks are drawn over water.** A boardwalk or a dock is drawn last, so it covers the water it crosses, and since the top layer decides a cell for navigation, a plank cell over water is walkable.
- **Movement costs stay at or above grass's 10.** The A* heuristic uses the profile's minimum cost as its step cost (see [SceneGeneration.md](SceneGeneration.md#terrain-layers-and-drawing-order)), so nothing is cheaper than grass.

## Phases

Each phase is done when its materials, tiles, palettes, terrain types and movement rules exist, the generators that should lay it do, the tests pass, and [Architecture.md](Architecture.md), [SceneGeneration.md](SceneGeneration.md) and this file are up to date. Tick the boxes as steps land.

### Phase 1: 16 layers

- [x] `TerrainControlMap`: `MaxLayers` 16, `ushort` cells, an `R16` texture (or the `RG8` fallback), shown and preview bits as `ushort`; `GetShownCell` and the preview API return and take 16 bits.
- [x] Shader: `TB_MAX_LAYERS` 16, the control map read as 16 bits, `TBTopLayer`, `TBMask` and every loop checked for 16; the lookup texture's rows for 16 layers.
- [x] Debug view: 16 distinct pure colours (each channel at 0, half or full, never mixed by the 2D lights in a way that confuses two layers), and `TerrainBlendProbe`'s classification (`DebugLayers`, `DebugClass`, `LayerNames`) for 16.
- [x] Checks: the renderer's build, `AreaGroundSetup` (writer and Convert Ground) and their messages allow 16.
- [x] Tests: a 16-layer renderer builds, draws every layer and previews strokes on the top one; the control map round-trips 16 bits; the debug colours are distinct; the writer accepts 16 layers and refuses 17; the existing terrain and generation suites still pass.
- [x] Measured with `TerrainBlendProbe.MeasureCost` (in a focused editor or a build): a 7-layer area before and after, and a 16-layer test area. Note the numbers in this file.

Notes:

- **The control map is `R16` (`R16_UNorm`).** Unity's texture format table lists "R 16 bit" as supported on Windows, macOS and Linux (partial on Android and iOS, which need the norm16 extension or Vulkan capability). D3D11 and D3D12 require `R16_UNORM` sampling; Vulkan leaves it optional, though desktop drivers support it. The renderer checks `SystemInfo.IsFormatSupported(GraphicsFormat.R16_UNorm, GraphicsFormatUsage.Sample)` (`TerrainControlMap.IsFormatSupported`) and logs an error and draws nothing on a device without it; `RG8` stays the fallback should a target need it. Each texel is the cell's 16 bits, written through `GetPixelData<ushort>` and read in the shader as `round(r * 65535)`, which needs full float precision there (desktop GPUs; a half-precision mobile shader would lose bits).
- **Debug colours.** `TB_DEBUG_COLOURS` keeps layers 0 to 6 as they were (red, green, yellow, blue, magenta, cyan, white) and 7 as orange, then rose, chartreuse, spring green, violet and azure (one channel full, another at half) and light yellow, light magenta and light cyan (two full, the third at half). The probe reads each channel as off, half or full against the brightest one, so the lights' intensity does not matter; the three colours left out (one channel full, two at half) read as "unknown colour".
- **Raising the arrays to 16 as they were made the shader too slow to compile and to draw.** With every per-layer loop unrolled over 16, one variant took over three minutes to compile (the shader compile test timed out at 180 s; at 8 the whole test takes 92 s). Turning the loops into loops over the area's layers fixed the compile time but, at 16, drew the Clearing up to 2.4 times slower (soft at zoom 3: 8.7 ms against 3.6), while the same loops capped at 8 cost what the old shader did: the per-pixel arrays sized for 16 (each layer's shape, and the distances and pair weights worked out again for every chip and stone) were the cost, not the loops. So the shader now reads a layer's shape from the lookup texture when it needs it (`TBShape`) instead of keeping 16 in registers, a chip's centre (`TBCentreAt`) and a whole chip's nearest depth (`TBDepthAt`) work out only the layers they need without arrays, and a pixel's distances and layers stop at the highest layer filled in its four cells (`TBLayersAt`), so an area pays per pixel for the layers painted there, not for the ones it lists. The shader compile test now takes 37 s. The Clearing, the Village Forest and the Lakeside render byte for byte as before the phase in both looks (captured at a fixed time before and after).
- **Cost**, best of three runs of 20 frames with the editor focused, the chunks shown, at 7680 x 4320 zoom 2 (the whole area in view), 7680 x 4320 zoom 3 (the area filling the frame) and 1920 x 1080 zoom 3, on the RTX 5070 Ti under D3D12; without the chunks a frame takes about 0.9, 0.9 and 0.65 ms:

  | | crisp (ms) | soft (ms) | full rebuild |
  |---|---|---|---|
  | The Clearing (7 layers), before | 1.85 / 2.95 / 0.96 | 2.21 / 3.57 / 1.11 | 6.9 ms |
  | The Clearing (7 layers), after | 1.71 / 2.70 / 0.93 | 2.11 / 3.19 / 1.09 | 6.3 ms |
  | 16 listed, the Clearing's 7 painted | 1.61 / 2.79 / 0.92 | 1.96 / 2.91 / 0.99 | |
  | 16 painted | 2.86 / 5.12 / 1.17 | 3.17 / 5.23 / 1.26 | 23 ms |

  The 16-layer area was a temporary, unsaved scene: a copy of the Clearing's grid and global light whose renderer listed nine more layers (sand, mud, gravel, stone, water, weeds, sand, mud, gravel, reusing the project's materials), each painted as four discs of radius 2 to 5 cells at fixed random spots, 1664 cells in all, so most of the area is crossed by edges between several layers, far busier than a real area. At 1080p it adds about 0.2 ms to the Clearing in either look. A rebuild takes four times as long, mostly copying 16 slices into each array. Each array holds a 512 px slice per layer (1 MiB), so the three take 48 MiB at 16 layers against 21 MiB at 7, as planned; the control map takes 2 bytes per cell instead of 1.

### Phase 2: per-area layer sets

Done before Phase 3, well ahead of the ocean (Phase 8), the 17th material. Since Phase 1 a listed but unpainted layer costs nothing per pixel, so the reasons were memory (each listed layer is a slice in each of the three texture arrays, as large as the area's largest material) and room for more than 16 materials, not frame time.

- [x] A project-wide draw order of ground materials (a list on `TerrainStyle`, see Decisions), and each generator's layers checked against it: a subsequence, at most 16, with an error otherwise.
- [x] Generators list only their own layers, at most 16. The Clearing and the Village Forest drop the ones they never use only if nothing is painted on them; Convert Ground keeps a painted layer an area has even when its generator no longer lists it, and warns.
- [x] `AreaLayoutBuilder` indexes layers by material or terrain type instead of fixed constants, since an index now depends on the area.
- [x] The area template holds the full current set, so a new area can be painted with anything, and its generator trims it.
- [x] The Terrain Brush and `TilePaletteFollower` work with any set, and the palette window only offers palettes for the area's layers (or says when a palette's material is not one of them).
- [x] Tests: generators' lists in the shared order, an area without a layer still drawing and navigating, Convert Ground adding and keeping layers.

Notes:

- **The check.** `AreaGroundSetup.Problem` gives the first reason a generator's layers cannot be set up: no style, more than 16 layers, a layer without a tilemap name, tile or material, two layers of one tilemap or one material, a material the style's order does not list, or a layer listed before one it comes after in that order. It is an error, not a warning: the writer and Convert Ground refuse to run (`CanSetUp` logs it), and the Scene Generator window shows it in an error box with Generate and Convert Ground disabled. Letting a layer through out of order would draw its pairs the other way up from every other area and change what the pair overrides mean, and there is nothing to gain from it.
- **How layouts address layers.** An `AreaLayout` carries the generator's layers (`TerrainLayers`), so a cell's layer is an index into that generator's list, which differs between generators. The generators reach a layer through their own `TerrainLayer` field (`TerrainCells(layer)`; `AreaLayoutBuilder` takes the generator's grass, gravel and stone layers for the shared steps), and tests and tools by material (`IndexOf(material)`). `AreaLayoutBuilder`'s `GrassLayer`…`WaterLayer` and `LayerCount` constants are gone. The writer refuses a layout whose layers are not the generator's (another count, or another material at an index).
- **What the scenes held.** Before trimming, every area listed all seven layers. Area_Clearing had sand (109 cells), mud (78) and water (81) painted by hand and no weeds, so the Clearing keeps sand, mud and water (still generated empty) and drops weeds: grass, sand, mud, gravel, stone, water. Area_VillageForest had nothing on weeds, sand, mud or water, so the Village Forest lists grass, gravel and stone. The Lakeside lays all seven and keeps them; Convert Ground on Area_Lakeside changes nothing.
- **Layers a generator does not list.** The writer and Convert Ground (`AreaGroundSetup.SetUpLayers`) keep a layer the area's renderer draws but the generator does not list when it is painted or the area's `AreaTerrain` lists it (gameplay may paint it at runtime), drawn at its material's place in the shared order, with a warning naming it; a layer whose material the order does not list stays drawn above the others, with a warning. An empty one is no longer drawn and its tilemap, a child of the grid, is removed. Convert Ground removed WeedsTilemap from Area_Clearing, and WeedsTilemap, SandTilemap, MudTilemap and WaterTilemap from Area_VillageForest; the renumbered navigation priorities and the renderer's list are the only other changes in either scene (compared object by object).
- **Undo order.** Restoring a removed child, or moving a child back to its old place, has Unity enable the grid's renderer again in the middle of the undo, and it then checks that each layer's navigation priority is its index. So `SetUpLayers` records the removals first, then the moves among the grid's children, then the navigation priorities, then the renderer's list: an undo reverts them in reverse, and the renderer only ever sees its old list with its old priorities. Recorded in the other order, a test's undo logged a priority mismatch.
- **The template** already held all seven layers, empty, in the shared order, and is unchanged. `AreaTemplateTests` now checks that it holds exactly the style's order, and that writing each generator's layout into it removes the layers the generator does not list.
- **The palette.** Unity's Tile Palette window lists every palette in the project and has no public way to filter that list, so it cannot offer only the area's palettes. Instead, the Terrain Brush's section of the window (`TerrainBrushEditor.OnPaintInspectorGUI`) warns when the picked tile belongs to a ground material (`TerrainTileWriter.MaterialOf`) that the target layer is not drawn with: it names the area's layer for that material, or says the area has no layer for it and that adding the layer to the area's generator and running Convert Ground gives it one. `TilePaletteFollower` already worked with any set, since it looks up the target layer's material through its renderer. The Scene Generator's map now colours each layer with its material's base colour (a shade darker when a layer below has the same colour, as weeds over grass) instead of by index.
- **Multiplayer.** `AreaTerrain`'s runtime edits (`TerrainEdit`) name a layer by its index in `AreaTerrain`'s own list (GrassTilemap and CollisionTilemap in every area), not by its index in the renderer, so trimming the renderer's layers changes nothing for them. Host and clients load the same saved scene (Multiplayer.md, scene content), so they hold the same list and agree on every index; the renderer's indices and control map bits are drawn locally and never sent. Convert Ground and the writer never remove a tilemap `AreaTerrain` lists.
- **Memory**, from the renderer's arrays after a build (each slice as large as the area's largest material, RGBA32; `Profiler.GetRuntimeMemorySizeLong` reports twice these figures in the editor):

  | | layers | albedo, cell field and height arrays | lookup texture |
  |---|---|---|---|
  | Area_Clearing, before | 7 | 3 x 512 x 512 x 7 = 21 MiB | 37 x 64 texels, 37 KiB |
  | Area_Clearing, after | 6 | 3 x 512 x 512 x 6 = 18 MiB | 37 x 49, 28 KiB |
  | Area_VillageForest, before | 7 | 3 x 512 x 512 x 7 = 21 MiB | 37 x 64, 37 KiB |
  | Area_VillageForest, after | 3 | 3 x 128 x 128 x 3 = 576 KiB | 37 x 16, 9 KiB |

  The Village Forest no longer lists sand or mud, whose textures repeat over 16 cells (512 px), so its slices shrink to grass's, gravel's and stone's 128 px as well as dropping in number. The control map is unchanged (2 bytes per cell).
- **Renders.** Area_Clearing and Area_VillageForest captured with `TerrainBlendProbe.Capture` over the control map's bounds, one screen pixel per art pixel, at a fixed time of 1.5 s (`SetFixedTime`), in both looks, at HEAD before any change of this phase (the tree was clean, the same as a `git stash -u` build) and after Convert Ground: all four pairs are byte for byte identical. The draw order and the navigation order of the remaining layers are unchanged, only their indices are.

### Phase 3: dirt, dry grass, plaza

The materials that need nothing new in the shader.

- [x] `Dirt` from a dirt recipe (the mud recipe's ground without puddles, with cracks and stones), edges over grass with a fringe of dry blades, over sand and mud with a rim.
- [x] `DryGrass` from the grass recipe in straw colours, seamless over grass.
- [x] `Plaza` from the stone recipe on a regular grid of seeds (no jitter), with larger slabs and straighter mortar.
- [x] Generators: dirt along the Village Forest's trails near the village and around a campsite in the Clearing; the plaza for the village square; dry grass in patches of the Lakeside's open grass.

Notes:

- **Texture size: every new material repeats over 4 cells (128 px)**, dry grass over 8 since its colour patches (see the materials as made below). An area's slices are as large as its largest material, so a 16-cell dirt like mud would take the Village Forest from 128 px slices to 512 px ones. Dirt is small marks on an even ground and needs no 16-cell repeat (mud's long repeat was for its puddles, which dirt has not); dry grass is the grass recipe and repeats with it; the plaza is a grid and repeats over whole slabs. So no new material raises an area's slice size. Memory of the three texture arrays (RGBA32, a slice per layer) and the lookup texture (37 texels by 1 + L + L(L + 1) rows of 16 bytes):

  | | layers, before | after | arrays, before | after | lookup texture, before | after |
  |---|---|---|---|---|---|---|
  | Area_Clearing | 6, 512 px | 4 (dirt; sand, mud and water dropped), 128 px | 18 MiB | 768 KiB | 28 KiB | 14 KiB |
  | Area_VillageForest | 3, 128 px | 5 (dirt, plaza), 128 px | 576 KiB | 960 KiB | 9 KiB | 21 KiB |
  | Area_Lakeside | 7, 512 px | 8 (dry grass), 512 px | 21 MiB | 24 MiB | 37 KiB | 47 KiB |

  Read back from the built renderers: the Clearing's arrays are 128 px by 4 slices with a 37 x 25 lookup texture, the Village Forest's 128 px by 5 with 37 x 36, the Lakeside's 512 px by 8 with 37 x 81. The Clearing was planned at 7 layers and 21 MiB, keeping its hand-painted sand, mud and water; it shrank instead when those went (see Regenerating).

- **Places in the shared order**, from the full order in Decisions: grass, dry grass, weeds, dirt, sand, mud, gravel, plaza, stone, water. Dry grass comes right over the grass it dries, under weeds; dirt over every grass but under sand and mud; the plaza between gravel and stone, so where the street (stone) meets the square the street is drawn over the slabs and its cobbles run on past the square, as a street passes a square it opens onto. The generated square's disc touches the street rather than crossing it, so the two meet along the street's side.
- **Dirt meets sand and mud from below.** The Terrains table gave dirt "a rim over sand and mud", but with dirt under them in the shared order (a beach or a puddle lies on the earth, not under it) the pairs are sand over dirt and mud over dirt, drawn with sand's and mud's edges: their own rim and outline. Their default edges cast a green shadow, meant for grass, which reads as a stain on dirt, so the style gets an override for each with the same rim in an earth shadow. Gravel and stone over dirt (the Village Forest's trails and street meet the dirt) get the same treatment for the same reason.
- **Default edges and overrides.** Dirt's default edge is its edge over grass, which is also what it draws over dry grass, weeds and nothing: a rim of straw fading into the earth, a dark straw outline, a green shadow on the grass and tufts of straw blades, the "fringe of dry blades" (tufts are drawn in the rim's outer colour with the outline on their border, so the fringe is straw). Soft keeps the outline, the rim and the tufts, as grass's edge does. Dry grass's default edge is the grass's edge in straw colours (over nothing, at the map's edge); dry grass over grass is an override, seamless with no outline, rim or shadow, like weeds over grass, since the two share the grass recipe's tufts (at the same places, until dry grass's repeat grew to 8 cells), plus short straw tufts so the patch frays into the grass (see the checks below). The plaza's default edge is stone's (an earthy rim fading into mortar, an outline, a green shadow; soft: a band of mortar), and plaza over gravel copies stone over gravel's override. Stone over plaza is a new override like stone over gravel: a thin mortar rim, no outline, a neutral shadow, and whole cobbles in soft, so the street looks laid into the square. Weeds over dry grass, a pair the Lakeside first made (it no longer does, see Corners below) and a painter still can, became an override after the checks: weeds drew their default edge there, grass's fringe for the map's edge (a 9 px band of light greens, an outline and 4.5 px tufts), a bright stripe between the two grasses whose tufts, in soft, pinched off a 3 px blob of dry grass; now it is seamless with 3 px green tufts (52, 128, 50), dry grass over grass the other way round.
- **Recipes.** Dirt is `MudPuddlesRecipe` with its puddles and wet patches off (puddle and wet levels at 1, cluster amount 0: the cluster waves then only tint), lumps as small stones, and cracks, a new setting of the mud recipe that is off by default so mud's textures do not change: short lines of a dark crack colour that step to a neighbouring pixel at random, with a lit lip below and right of each crack pixel (the light comes from the top left). Dry grass is `GrassTuftsRecipe` with the grass recipe's seed and settings but straw colours, so its tufts first lay where the grass's do (no longer since it repeats over 8 cells, which nothing relies on: its edge over grass draws tufts of its own). The plaza is `StoneCobblesRecipe` with no jitter and two slabs per cell side (16 px). With no jitter the seeds sit on a regular grid and the cell edges are straight, but they fall between two pixels: with an even step a mortar width of 0.5 or less leaves no mortar and anything up to 1.5 gives two pixels, and a step that does not divide the texture gives slabs of uneven widths. So the stone recipe gets a new setting, a seed offset in pixels (0 by default, so stone does not change): half a pixel puts every cell edge on a pixel centre, which gives straight one-pixel mortar between square slabs.
- **Layouts.** Each new terrain is laid at the end of its generation, after the mobs, from a second random stream seeded from the layout's seed (`AreaLayoutBuilder.StartDetailStream`), so every draw before it, and so every path, prop and mob, stays where it was for every seed:
  - *The Village Forest's dirt*: shoulders along the gravel trails near the village: grass cells within a width of a trail cell, the width falling from `dirtWidth` (2 cells) at the junction to nothing `dirtReach` (18 cells) from it, its edge moved in and out by smooth noise, never in a lot. Dirt stays off the paths; it may run under a prop beside the trail (the trail's clearance keeps the nearest cell free of blocking props and the next of walk-through ones), since grass goes on under it and props stand on it as on grass.
  - *The Village Forest's square*: the same disc, now painted as plaza instead of stone (any street cell in it staying stone over it); the plaza counts as a path for the clearance, the path network and every check that read the square as stone, so nothing else in the layout moves.
  - *The Clearing's campsite*: a wobbly disc of dirt (`campsiteRadius`, 3 cells) on interior grass deeper than the edge band plus the radius, with no path within the radius plus the clearance and its radius clear of the spawn's disc and of every mob; the campfire stands in its middle and three seats (`Stump_Small`, `Stool_A`, `Stool_B`) on the dirt around it. As planned, with no blocking prop allowed in or beside the disc, half the seeds found no spot: the Clearing's interior is crowded with trees, bushes and rocks. So among the cells that qualify it takes one with the fewest cells under blocking props within the radius less half a cell, and removes those props (on 20 seeds, one tree in two of them); it also removes the plants on or beside the dirt, since a plant's sprite stands above its cell and one just below the patch grew over it. Props are only removed, so nothing else moves and reachability can only grow. The trodden track to the nearest path was dropped: through the scattered trees it would have run under trunks or zigzagged. The spawn's disc and every path keep their clearance, and the PlayMode tests' margins (spawn clear radius 6, mobs 14 cells away) are untouched.
  - *The Lakeside's dry grass*: `dryGrassPatchCount` wobbly patches of a radius between the two values of `dryGrassPatchRadius`, centred on open grass far from the lake (beyond the shore band and off the paths), on grass that is not water, beach or mud and not on or beside weeds or a path (see Corners below). Props stand on it as on grass.
- **Regenerating.** Area_VillageForest and Area_Lakeside held exactly their generators' layouts for seed 1 (every cell, prop, mob and the spawn compared). ## Testing

Each phase adds the tests the existing materials have: the recipe's determinism, PNGs and look (`TerrainMaterialRecipeTests`), the lookup texture's new settings (`TerrainBlendLutTests`), the tile and palette (`TerrainTileTests`), the generators' layouts over many seeds (`AreaGenerationTests`), and the template (`AreaTemplateTests`). Shader effects are checked by eye with `TerrainBlendProbe` captures at fixed times, in both looks, and noted in the phase's notes, as in TerrainBlending.md.

## Open questions

- **R16 or RG8: R16** (decided in Phase 1). Unity lists `R16` for every desktop platform we build for, D3D11 and D3D12 require it and desktop Vulkan drivers have it; the renderer refuses to draw on a device without it. `RG8` stays the fallback if a target ever lacks it. See Phase 1's notes.
- **Texture memory at 16 layers.** Every slice of an area's arrays is as large as its largest material's textures (512 px since mud and sand repeat over 16 cells). Phase 1 measured 48 MiB for 16 layers against 21 MiB for 7. Per-area sets (Phase 2) brought the Village Forest to 576 KiB and the Clearing to 18 MiB; after Phase 3 the Village Forest takes 960 KiB, the Clearing 768 KiB and the Lakeside 24 MiB (its sand and mud repeat over 16 cells). If an area that needs many layers is still too heavy, options are a cell field array only for the layers that have one, or smaller repeats for most materials.
- **Raised variants:** a second material asset per raised material is simple but doubles assets; a per-layer "raised" flag on the renderer keeps one material but makes the same material look different in two layers. To decide in Phase 10.
- **Tall grass as cover:** hiding units in tall grass is gameplay (visibility, targeting) and belongs in its own spec when we want it.
