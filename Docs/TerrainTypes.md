# Terrain types

Plan for 16 ground layers per area instead of 8, and for the next ground materials after grass, weeds, sand, mud, gravel, stone and water: dirt, dry grass, a flower meadow, tall grass, wooden planks, plaza tiles, shallow water, an ocean, lava, snow, ice and raised ground. [TerrainBlending.md](TerrainBlending.md) is the renderer they are drawn with and the phases that built it; [Architecture.md](Architecture.md) describes what exists. This file describes what to add and in which order.

Every rule in [Multiplayer.md](Multiplayer.md#rules-for-new-code-starting-now) applies. Ground is scene content every machine loads the same way, so a new material is drawn locally with nothing replicated. A terrain that changes gameplay (damage) does so on the server, through the systems that already own that gameplay.

## Where we start

The state before Phase 1; its notes say what changed.

- An area's ground is up to 8 layers: a control map stores each cell's layers as the bits of one byte (`TerrainControlMap`, an `R8` texture, `MaxLayers` 8), and the shader's per-pixel arrays are sized for 8 (`TB_MAX_LAYERS`). Every generator, every area and the area template list the same 7: grass, weeds, sand, mud, gravel, stone and water, in that draw order, which is also the navigation priority.
- The 8 is enforced in `TerrainControlMap.Build`, the renderer's build checks, `AreaGroundSetup` (the writer and Convert Ground refuse more, and drop drawn layers past 8 with a warning), and assumed by the debug view's colours (`TBDebugColour`: 7 pure colours and orange) and `TerrainBlendProbe`'s blob checks (`DebugLayers` 8). `AreaTerrain`'s runtime edits already index up to 256 layers.
- A material is a `TerrainMaterial` asset with textures written by its recipe (`TerrainMaterialRecipe` subclasses), a plain tile, a palette and a `TerrainType2D`, plus rules in `TerrainMovement_Default` when it is not walked like grass.
- What a material can already do in the shader: chips and stones from a cell field (gravel, stone), glints and sparkles (water), a swelling rim (water), sinking with a bank (water), swaying weeds (weeds), and a seamless edge over a material of the same look (weeds over grass).
- Generators: the Clearing, the Village Forest and the Lakeside (see [SceneGeneration.md](SceneGeneration.md)).

## Goals

- Up to 16 ground layers in one area, with the shader, the debug view, the probe, the brush preview and every check following.
- Every terrain listed above, paintable in any area that lists it, each with its own look, edge rules and movement.
- No area pays for layers it does not use: the per-pixel cost and the texture memory follow the layers an area lists, not the maximum.
- Shader features stay general: each new effect is a material setting another material can reuse, not a special case for one material.
- Every terrain a generator can lay is laid by at least one generator, and every terrain is covered by tests like the existing ones (recipe, lookup texture, generator layouts).

## Non-goals (for now)

- Footprints, tracks or any ground that changes while playing (snow you walk into, lava that spreads). Ground stays static scene content.
- Real elevation for gameplay: raised ground is a look, and its edges block movement only where walls would.
- Weather and seasons that switch materials at runtime.
- Water that flows. Shallows and the ocean animate inside a fixed shape, like the pond.
- Slipping on ice. Ice is walked like grass; sliding units are out of scope (decided in Phase 7).

## Decisions

- **16 layers, from a 16-bit control map.** The control map moves from `R8` to `R16` (one 16-bit channel; each texel's value is the cell's layer bits, read in the shader as `round(r * 65535)`), its cells from bytes to `ushort`s, and `MaxLayers` and `TB_MAX_LAYERS` to 16. `R16` is supported for sampling on the platforms we build for (Windows, D3D11/12 and Vulkan); the renderer checks `SystemInfo.IsFormatSupported` for sampling and fails loudly otherwise, and `RG8` (low and high bytes in two channels) is the fallback if a target lacks it. Check the format against Unity's docs before building it.
- **The cost follows the layers an area lists.** The shader's loops already stop at the area's layer count (`ins.layers`), so an area of 7 layers does the same work under a 16-layer shader as today; only the arrays (distances, pair weights, shapes) grow, which raises register use. The lookup texture grows with the layers (1 + L + L(L + 1) rows: 57 for 7, 289 for 16) and the albedo, cell field and height arrays get a slice per layer, so 16 layers at 512 px is about 48 MB on the GPU against 19 MB for 7 today. Measure a 16-layer area against a 7-layer one before calling the phase done. Phase 1 found the arrays did matter and removed them from the per-pixel work; a pixel now pays only for the layers filled around it (see Phase 1's notes).
- **Per-area layer sets, before the project passes 16 materials.** The planned materials add up to 18 layers, more than one area can hold even at 16. Each generator will list only the layers its area uses, in the shared order, which also keeps memory and register use down. The renderer already draws whatever list a grid gives it, so this is generator, writer, template and test work; it must land before the 17th material (the ocean, Phase 8).
- **One shared draw order.** Layers keep a project-wide order, so a pair looks the same in every area and pair overrides keep their meaning: each area's list is a subsequence of it. The order, bottom first: grass, dry grass, meadow, tall grass, snow, dirt, sand, mud, ice, gravel, plaza, stone, shallows, water, ocean, lava, planks. Raised ground is not a layer (see Phase 10). Weeds were in it, right over the grass, until Phase 3 merged them into grass.
- **The shared order is a list on `TerrainStyle`**, `layerOrder` (decided in Phase 2), not a separate `TerrainLayerOrder` asset. The order exists so that a pair is always the same upper material over the same lower one, which is exactly what the style's pair overrides are keyed on, so the order and the overrides describe one thing, the edges between materials, and change together. Every generator and every area's renderer already names its style, so the writer, Convert Ground, the brush and the tests reach the order with no new reference, asset lookup or service. The cost: a second style would carry an order of its own. If the project ever has several styles, move the list to an asset they share. The list holds only the materials that exist (seven until Phase 3: grass, weeds, sand, mud, gravel, stone, water; nine after it: grass, dry grass, dirt, sand, mud, gravel, plaza, stone, water, weeds having merged into grass; ten since Phase 4, with shallows between stone and water; eleven since Phase 5, with planks last; thirteen since Phase 6, with meadow and tall grass after dry grass; fifteen since Phase 7, with snow after tall grass and ice after mud); a new material goes in at its place from the full order above.
- **Planks are drawn over water.** A boardwalk or a dock is drawn last, so it covers the water it crosses, and since the top layer decides a cell for navigation, a plank cell over water is walkable.
- **Movement costs stay at or above grass's 10.** The A* heuristic uses the profile's minimum cost as its step cost (see [SceneGeneration.md](SceneGeneration.md#terrain-layers-and-drawing-order)), so nothing is cheaper than grass.

## Phases

Each phase is done when its materials, tiles, palettes, terrain types and movement rules exist, the generators that should lay it do, the tests pass, and [Architecture.md](Architecture.md), [SceneGeneration.md](SceneGeneration.md) and this file are up to date. Tick the boxes as steps land.

### Phase 1: 16 layers

- [x] `TerrainControlMap`: `MaxLayers` 16, `ushort` cells, an `R16` texture (or the `RG8` fallback), shown and preview bits as `ushort`; `GetShownCell` and the preview API return and take 16 bits.
- [x] Shader: `TB_MAX_LAYERS` 16, the control map read as 16 bits, `TBTopLayer`, `TBMask` and every loop checked for 16; the lookup texture's rows for 16 layers.
- [x] Debug view: 16 distinct pure colours (each channel at 0, half or full, never mixed by the 2D lights in a way that confuses two layers), and `TerrainBlendProbe`'s classification (`DebugLayers`, `DebugClass`, `LayerNames`) for 16.
- [x] Checks: the renderer's build, `AreaGroundSetup` (writer and Convert Ground) and their messages allow 16.
- [x] Tests: a 16-layer renderer builds, draws every layer and previews strokes on the top one; the control map round-trips 16 bits; the debug colours are distinct; the writer accepts 16 layers and refuses 17; the existing terrain and generation suites still pass.
- [x] Measured with `TerrainBlendProbe.MeasureCost` (in a focused editor or a build): a 7-layer area before and after, and a 16-layer test area. Note the numbers in this file.

Notes:

- **The control map is `R16` (`R16_UNorm`).** Unity's texture format table lists "R 16 bit" as supported on Windows, macOS and Linux (partial on Android and iOS, which need the norm16 extension or Vulkan capability). D3D11 and D3D12 require `R16_UNORM` sampling; Vulkan leaves it optional, though desktop drivers support it. The renderer checks `SystemInfo.IsFormatSupported(GraphicsFormat.R16_UNorm, GraphicsFormatUsage.Sample)` (`TerrainControlMap.IsFormatSupported`) and logs an error and draws nothing on a device without it; `RG8` stays the fallback should a target need it. Each texel is the cell's 16 bits, written through `GetPixelData<ushort>` and read in the shader as `round(r * 65535)`, which needs full float precision there (desktop GPUs; a half-precision mobile shader would lose bits).
- **Debug colours.** `TB_DEBUG_COLOURS` keeps layers 0 to 6 as they were (red, green, yellow, blue, magenta, cyan, white) and 7 as orange, then rose, chartreuse, spring green, violet and azure (one channel full, another at half) and light yellow, light magenta and light cyan (two full, the third at half). The probe reads each channel as off, half or full against the brightest one, so the lights' intensity does not matter; the three colours left out (one channel full, two at half) read as "unknown colour".
- **Raising the arrays to 16 as they were made the shader too slow to compile and to draw.** With every per-layer loop unrolled over 16, one variant took over three minutes to compile (the shader compile test timed out at 180 s; at 8 the whole test takes 92 s). Turning the loops into loops over the area's layers fixed the compile time but, at 16, drew the Clearing up to 2.4 times slower (soft at zoom 3: 8.7 ms against 3.6), while the same loops capped at 8 cost what the old shader did: the per-pixel arrays sized for 16 (each layer's shape, and the distances and pair weights worked out again for every chip and stone) were the cost, not the loops. So the shader now reads a layer's shape from the lookup texture when it needs it (`TBShape`) instead of keeping 16 in registers, a chip's centre (`TBCentreAt`) and a whole chip's nearest depth (`TBDepthAt`) work out only the layers they need without arrays, and a pixel's distances and layers stop at the highest layer filled in its four cells (`TBLayersAt`), so an area pays per pixel for the layers painted there, not for the ones it lists. The shader compile test now takes 37 s. The Clearing, the Village Forest and the Lakeside render byte for byte as before the phase in both looks (captured at a fixed time before and after).
- **Cost**, best of three runs of 20 frames with the editor focused, the chunks shown, at 7680 x 4320 zoom 2 (the whole area in view), 7680 x 4320 zoom 3 (the area filling the frame) and 1920 x 1080 zoom 3, on the RTX 5070 Ti under D3D12; without the chunks a frame takes about 0.9, 0.9 and 0.65 ms:

  | | crisp (ms) | soft (ms) | full rebuild |
  |---|---|---|---|
  | The Clearing (7 layers), before | 1.85 / 2.95 / 0.96 | 2.21 / 3.57 / 1.11 | 6.9 ms |
  | The Clearing (7 layers), after | 1.71 / 2.70 / 0.93 | 2.11 / 3.19 / 1.09 | 6.3 ms |
  | 16 listed, the Clearing's 7 painted | 1.61 / 2.79 / 0.92 | 1.96 / 2.91 / 0.99 | |
  | 16 painted | 2.86 / 5.12 / 1.17 | 3.17 / 5.23 / 1.26 | 23 ms |

  The 16-layer area was a temporary, unsaved scene: a copy of the Clearing's grid and global light whose renderer listed nine more layers (sand, mud, gravel, stone, water, weeds, sand, mud, gravel, reusing the project's materials), each painted as four discs of radius 2 to 5 cells at fixed random spots, 1664 cells in all, so most of the area is crossed by edges between several layers, far busier than a real area. At 1080p it adds about 0.2 ms to the Clearing in either look. A rebuild takes four times as long, mostly copying 16 slices into each array. Each array holds a 512 px slice per layer (1 MiB), so the three take 48 MiB at 16 layers against 21 MiB at 7, as planned; the control map takes 2 bytes per cell instead of 1.

### Phase 2: per-area layer sets

Done before Phase 3, well ahead of the ocean (Phase 8), the 17th material. Since Phase 1 a listed but unpainted layer costs nothing per pixel, so the reasons were memory (each listed layer is a slice in each of the three texture arrays, as large as the area's largest material) and room for more than 16 materials, not frame time.

- [x] A project-wide draw order of ground materials (a list on `TerrainStyle`, see Decisions), and each generator's layers checked against it: a subsequence, at most 16, with an error otherwise.
- [x] Generators list only their own layers, at most 16. The Clearing and the Village Forest drop the ones they never use only if nothing is painted on them; Convert Ground keeps a painted layer an area has even when its generator no longer lists it, and warns.
- [x] `AreaLayoutBuilder` indexes layers by material or terrain type instead of fixed constants, since an index now depends on the area.
- [x] The area template holds the full current set, so a new area can be painted with anything, and its generator trims it.
- [x] The Terrain Brush and `TilePaletteFollower` work with any set, and the palette window only offers palettes for the area's layers (or says when a palette's material is not one of them).
- [x] Tests: generators' lists in the shared order, an area without a layer still drawing and navigating, Convert Ground adding and keeping layers.

Notes:

- **The check.** `AreaGroundSetup.Problem` gives the first reason a generator's layers cannot be set up: no style, more than 16 layers, a layer without a tilemap name, tile or material, two layers of one tilemap or one material, a material the style's order does not list, or a layer listed before one it comes after in that order. It is an error, not a warning: the writer and Convert Ground refuse to run (`CanSetUp` logs it), and the Scene Generator window shows it in an error box with Generate and Convert Ground disabled. Letting a layer through out of order would draw its pairs the other way up from every other area and change what the pair overrides mean, and there is nothing to gain from it.
- **How layouts address layers.** An `AreaLayout` carries the generator's layers (`TerrainLayers`), so a cell's layer is an index into that generator's list, which differs between generators. The generators reach a layer through their own `TerrainLayer` field (`TerrainCells(layer)`; `AreaLayoutBuilder` takes the generator's grass, gravel and stone layers for the shared steps), and tests and tools by material (`IndexOf(material)`). `AreaLayoutBuilder`'s `GrassLayer`…`WaterLayer` and `LayerCount` constants are gone. The writer refuses a layout whose layers are not the generator's (another count, or another material at an index).
- **What the scenes held.** Before trimming, every area listed all seven layers. Area_Clearing had sand (109 cells), mud (78) and water (81) painted by hand and no weeds, so the Clearing keeps sand, mud and water (still generated empty) and drops weeds: grass, sand, mud, gravel, stone, water. Area_VillageForest had nothing on weeds, sand, mud or water, so the Village Forest lists grass, gravel and stone. The Lakeside lays all seven and keeps them; Convert Ground on Area_Lakeside changes nothing.
- **Layers a generator does not list.** The writer and Convert Ground (`AreaGroundSetup.SetUpLayers`) keep a layer the area's renderer draws but the generator does not list when it is painted or the area's `AreaTerrain` lists it (gameplay may paint it at runtime), drawn at its material's place in the shared order, with a warning naming it; a layer whose material the order does not list stays drawn above the others, with a warning. An empty one is no longer drawn and its tilemap, a child of the grid, is removed. Convert Ground removed WeedsTilemap from Area_Clearing, and WeedsTilemap, SandTilemap, MudTilemap and WaterTilemap from Area_VillageForest; the renumbered navigation priorities and the renderer's list are the only other changes in either scene (compared object by object).
- **Undo order.** Restoring a removed child, or moving a child back to its old place, has Unity enable the grid's renderer again in the middle of the undo, and it then checks that each layer's navigation priority is its index. So `SetUpLayers` records the removals first, then the moves among the grid's children, then the navigation priorities, then the renderer's list: an undo reverts them in reverse, and the renderer only ever sees its old list with its old priorities. Recorded in the other order, a test's undo logged a priority mismatch.
- **The template** already held all seven layers, empty, in the shared order, and is unchanged. `AreaTemplateTests` now checks that it holds exactly the style's order, and that writing each generator's layout into it removes the layers the generator does not list.
- **The palette.** Unity's Tile Palette window lists every palette in the project and has no public way to filter that list, so it cannot offer only the area's palettes. Instead, the Terrain Brush's section of the window (`TerrainBrushEditor.OnPaintInspectorGUI`) warns when the picked tile belongs to a ground material (`TerrainTileWriter.MaterialOf`) that the target layer is not drawn with: it names the area's layer for that material, or says the area has no layer for it and that adding the layer to the area's generator and running Convert Ground gives it one. `TilePaletteFollower` already worked with any set, since it looks up the target layer's material through its renderer. The Scene Generator's map now colours each layer with its material's base colour (a shade darker when a layer below has the same colour, as weeds over grass) instead of by index.
- **Multiplayer.** `AreaTerrain`'s runtime edits (`TerrainEdit`) name a layer by its index in `AreaTerrain`'s own list (GrassTilemap and CollisionTilemap in every area), not by its index in the renderer, so trimming the renderer's layers changes nothing for them. Host and clients load the same saved scene (Multiplayer.md, scene content), so they hold the same list and agree on every index; the renderer's indices and control map bits are drawn locally and never sent. Convert Ground and the writer never remove a tilemap `AreaTerrain` lists.
- **Memory**, from the renderer's arrays after a build (each slice as large as the area's largest material, RGBA32; `Profiler.GetRuntimeMemorySizeLong` reports twice these figures in the editor):

  | | layers | albedo, cell field and height arrays | lookup texture |
  |---|---|---|---|
  | Area_Clearing, before | 7 | 3 x 512 x 512 x 7 = 21 MiB | 37 x 64 texels, 37 KiB |
  | Area_Clearing, after | 6 | 3 x 512 x 512 x 6 = 18 MiB | 37 x 49, 28 KiB |
  | Area_VillageForest, before | 7 | 3 x 512 x 512 x 7 = 21 MiB | 37 x 64, 37 KiB |
  | Area_VillageForest, after | 3 | 3 x 128 x 128 x 3 = 576 KiB | 37 x 16, 9 KiB |

  The Village Forest no longer lists sand or mud, whose textures repeat over 16 cells (512 px), so its slices shrink to grass's, gravel's and stone's 128 px as well as dropping in number. The control map is unchanged (2 bytes per cell).
- **Renders.** Area_Clearing and Area_VillageForest captured with `TerrainBlendProbe.Capture` over the control map's bounds, one screen pixel per art pixel, at a fixed time of 1.5 s (`SetFixedTime`), in both looks, at HEAD before any change of this phase (the tree was clean, the same as a `git stash -u` build) and after Convert Ground: all four pairs are byte for byte identical. The draw order and the navigation order of the remaining layers are unchanged, only their indices are.

### Phase 3: dirt, dry grass, plaza

The materials that need nothing new in the shader (it did gain, after the phase, a check that hides grass clumps at borders, see the notes).

- [x] `Dirt` from a dirt recipe (the mud recipe's ground without puddles, with cracks and stones), edges over grass with a fringe of dry blades, over sand and mud with a rim.
- [x] `DryGrass` from the grass recipe in straw colours, seamless over grass.
- [x] `Plaza` from the stone recipe on a regular grid of seeds (no jitter), with larger slabs and straighter mortar.
- [x] Generators: dirt along the Village Forest's trails near the village and around a campsite in the Clearing; the plaza for the village square; dry grass in patches of the Lakeside's open grass.

Notes:

- **Texture size: every new material repeats over 4 cells (128 px)**, dry grass over 8 since its colour patches (see the materials as made below). An area's slices are as large as its largest material, so a 16-cell dirt like mud would take the Village Forest from 128 px slices to 512 px ones. Dirt is small marks on an even ground and needs no 16-cell repeat (mud's long repeat was for its puddles, which dirt has not); dry grass is the grass recipe and repeats with it; the plaza is a grid and repeats over whole slabs. So no new material raises an area's slice size. Memory of the three texture arrays (RGBA32, a slice per layer) and the lookup texture (37 texels by 1 + L + L(L + 1) rows of 16 bytes):

  | | layers, before | after | arrays, before | after | lookup texture, before | after |
  |---|---|---|---|---|---|---|
  | Area_Clearing | 6, 512 px | 4 (dirt; sand, mud and water dropped), 128 px, 256 px since grass's 8-cell repeat | 18 MiB | 768 KiB, then 3 MiB | 28 KiB | 14 KiB |
  | Area_VillageForest | 3, 128 px | 5 (dirt, plaza), 128 px, then 256 px | 576 KiB | 960 KiB, then 3.75 MiB | 9 KiB | 21 KiB |
  | Area_Lakeside | 7, 512 px | 8 (dry grass), 512 px; 7 since weeds merged into grass | 21 MiB | 24 MiB, then 21 MiB | 37 KiB | 47 KiB, then 37 KiB |

  Read back from the built renderers: the Clearing's arrays are 128 px by 4 slices with a 37 x 25 lookup texture, the Village Forest's 128 px by 5 with 37 x 36, the Lakeside's 512 px by 8 with 37 x 81. The Clearing was planned at 7 layers and 21 MiB, keeping its hand-painted sand, mud and water; it shrank instead when those went (see Regenerating).

- **Places in the shared order**, from the full order in Decisions: grass, dry grass, weeds, dirt, sand, mud, gravel, plaza, stone, water. Dry grass comes right over the grass it dries, under weeds; dirt over every grass but under sand and mud; the plaza between gravel and stone, so where the street (stone) meets the square the street is drawn over the slabs and its cobbles run on past the square, as a street passes a square it opens onto. The generated square's disc touches the street rather than crossing it, so the two meet along the street's side.
- **Dirt meets sand and mud from below.** The Terrains table gave dirt "a rim over sand and mud", but with dirt under them in the shared order (a beach or a puddle lies on the earth, not under it) the pairs are sand over dirt and mud over dirt, drawn with sand's and mud's edges: their own rim and outline. Their default edges cast a green shadow, meant for grass, which reads as a stain on dirt, so the style gets an override for each with the same rim in an earth shadow. Gravel and stone over dirt (the Village Forest's trails and street meet the dirt) get the same treatment for the same reason.
- **Default edges and overrides.** Dirt's default edge is its edge over grass, which is also what it draws over dry grass, weeds and nothing: a rim of straw fading into the earth, a dark straw outline, a green shadow on the grass and tufts of straw blades, the "fringe of dry blades" (tufts are drawn in the rim's outer colour with the outline on their border, so the fringe is straw). Soft keeps the outline, the rim and the tufts, as grass's edge does. Dry grass's default edge is the grass's edge in straw colours (over nothing, at the map's edge); dry grass over grass is an override, seamless with no outline, rim or shadow, like weeds over grass, since the two share the grass recipe's tufts (at the same places, until dry grass's repeat grew to 8 cells), plus short straw tufts so the patch frays into the grass (see the checks below). The plaza's default edge is stone's (an earthy rim fading into mortar, an outline, a green shadow; soft: a band of mortar), and plaza over gravel copies stone over gravel's override. Stone over plaza is a new override like stone over gravel: a thin mortar rim, no outline, a neutral shadow, and whole cobbles in soft, so the street looks laid into the square. Weeds over dry grass, a pair the Lakeside first made (it no longer does, see Corners below) and a painter still can, became an override after the checks: weeds drew their default edge there, grass's fringe for the map's edge (a 9 px band of light greens, an outline and 4.5 px tufts), a bright stripe between the two grasses whose tufts, in soft, pinched off a 3 px blob of dry grass; now it is seamless with 3 px green tufts (52, 128, 50), dry grass over grass the other way round.
- **Recipes.** Dirt is `MudPuddlesRecipe` with its puddles and wet patches off (puddle and wet levels at 1, cluster amount 0: the cluster waves then only tint), lumps as small stones, and cracks, a new setting of the mud recipe that is off by default so mud's textures do not change: short lines of a dark crack colour that step to a neighbouring pixel at random, with a lit lip below and right of each crack pixel (the light comes from the top left). Dry grass was planned as `GrassTuftsRecipe` alone (now its ground, under weeds-recipe stalks, see the materials as made) with the grass recipe's seed and settings but straw colours, so its tufts first lay where the grass's do (no longer since it repeats over 8 cells, which nothing relies on: its edge over grass draws tufts of its own). The plaza is `StoneCobblesRecipe` with no jitter and two slabs per cell side (16 px). With no jitter the seeds sit on a regular grid and the cell edges are straight, but they fall between two pixels: with an even step a mortar width of 0.5 or less leaves no mortar and anything up to 1.5 gives two pixels, and a step that does not divide the texture gives slabs of uneven widths. So the stone recipe gets a new setting, a seed offset in pixels (0 by default, so stone does not change): half a pixel puts every cell edge on a pixel centre, which gives straight one-pixel mortar between square slabs.
- **Layouts.** Each new terrain is laid at the end of its generation, after the mobs, from a second random stream seeded from the layout's seed (`AreaLayoutBuilder.StartDetailStream`), so every draw before it, and so every path, prop and mob, stays where it was for every seed:
  - *The Village Forest's dirt*: shoulders along the gravel trails near the village: grass cells within a width of a trail cell, the width falling from `dirtWidth` (2 cells) at the junction to nothing `dirtReach` (18 cells) from it, its edge moved in and out by smooth noise, never in a lot. Dirt stays off the paths; it may run under a prop beside the trail (the trail's clearance keeps the nearest cell free of blocking props and the next of walk-through ones), since grass goes on under it and props stand on it as on grass.
  - *The Village Forest's square*: the same disc, now painted as plaza instead of stone (any street cell in it staying stone over it); the plaza counts as a path for the clearance, the path network and every check that read the square as stone, so nothing else in the layout moves.
  - *The Clearing's campsite*: a wobbly disc of dirt (`campsiteRadius`, 3 cells) on interior grass deeper than the edge band plus the radius, with no path within the radius plus the clearance and its radius clear of the spawn's disc and of every mob; the campfire stands in its middle and three seats (`Stump_Small`, `Stool_A`, `Stool_B`) on the dirt around it. As planned, with no blocking prop allowed in or beside the disc, half the seeds found no spot: the Clearing's interior is crowded with trees, bushes and rocks. A first version put the joints on the joists (every 16 px), which left 8 px stubs of boards along the sides of every dock, since a generated dock's sides lie on cell borders; with the joints on the cell borders a dock of whole cells shows whole boards or boards cut at a cell border.
- **The cell field points across each board.** A cut stone is decided at its centre (left out when the centre lies in the rim) and cut along the rim. A board can be longer than a dock is wide, so its centre often lies off the dock and the whole board would be left out. So every pixel points straight across its board, at the board's middle row in its own column, which points at itself as the contract asks; its alpha is its distance to the board's edge (the gap rows and the joints, on pixel centres), so the shader cuts a board along the dock's sides and bevels the cut end to the light (cut bevel 18, no cut gap), and leaves out a board only where its middle row lies in the rim (keep margin -0.5 px), which a dock's ends, on cell borders like the gaps, never do.
- **Repeat and memory.** The planks repeat over 8 cells (256 px), so a dock of up to 8 cells shows no repeat of its boards' colours and joints, and no area's slices grow: the Lakeside's are 512 px (sand and mud), the Clearing's and the Village Forest's 256 px (grass). The Lakeside goes from 8 layers to 9: its three arrays from 3 x 512 x 512 x 8 RGBA32 (24 MiB) to 3 x 512 x 512 x 9 (27 MiB), its lookup texture from 37 x 81 texels (47 KiB) to 37 x 100 (58 KiB).
- **Orientation: a material setting, Turn To Runs, worked out per cell by the shader.** The boards lie along the texture's x, so they cross a dock or boardwalk running up and down. Weighed:
  - *Two fixed orientations as two materials*: no shader work, and a painter chooses the orientation cell by cell from two palettes. But it doubles the assets, an area using both pays a second layer and a second slice in each array (3 MiB at the Lakeside's 512 px), and where the two meet they make a pair whose rounded corners show the lower one beside the upper where both meet water (Phase 3's Corners note).
  - *One orientation, the generator running its docks up and down*: no cost at all, but a painted east-west boardwalk would run its boards along it.
  - *Per cell, from the neighbouring plank cells*: one material and one layer for any direction, nothing to choose; the cost is in the shader. Phase 1's lesson was that per-pixel arrays sized for 16 layers cost registers and draw time, and loops unrolled over 16 cost compile time; this needs neither: a turning layer's interior pixel reads up to 12 control map texels in four loops that stop at the first cell without the layer, and every interior pixel of every layer one more lookup texel for the flag (in the soft look, also every pixel of a layer with a cell field). The flaw is that it is a guess: at junctions, in platforms wider than 3 cells, and at the ends of walkways wider than 3 cells, it may turn some cells and not others, and a painter cannot override it.

  The per-cell turn was chosen: it is a general setting another material can use (crop rows, rails, a rope bridge), no area pays for it unless it draws a turning layer, and a straight dock or boardwalk, what the generator lays and what a painter mostly paints, always comes out right. The rule (`TBTurned`): a cell turns its textures when the layer covers more cells left and right of it than up and down, counting up to 3 each way, a tie keeping them as they are. A turned cell reads its textures turned a quarter, the texture's x going up the world and its top to the left, so a board's lit top row becomes its lit left side; the cell field's offsets, a swaying clump's lean and its rows turn back into the world with it (`TBUnturn`). Because the gaps and joints lie on the cell borders, a turned cell meets an unturned one along a gap or a board's dark edge. A T-shaped test dock (a 2-cell stem under an 8 x 2 head) turned its whole head and none of its stem. The soft look's heights are read as they are in every cell: they only move edges, and the planks' height scale is 0, so a dock's edges stay straight there (at 1 px its sides stepped by a pixel where the height crossed a pixel).
- **A bridge: lower layers do not go on under the planks.** Every layer's shape counts the cells of every layer above it (lower layers go on under upper ones). Planks over water would then carry the water, and the shallows, stone and gravel between them, under the whole dock, its beach end included: where the dock crosses the shore, the water's shape would take in the dock's beach cells and its 11 px inner fillets would show water on the sand beside the dock, a third look under a corner, and the trail's gravel would run on under the dock. A material setting, Bridge, makes a layer lie on what is painted under it: a lower layer's shape counts a bridge layer's cells only where that lower layer (or a layer above it that is no bridge) is painted (`TBCounted`, from a bit per bridge layer in the lookup texture's row 0). So the water goes on under the dock where the lake is, and beside its beach end the shore runs straight up to its sides. It costs two integer operations per cell of each layer's mask and nothing else; with no bridge the bits are 0 and every area renders as before.
- **Byte for byte.** With the shader changes (bridges and turning), the Clearing, the Village Forest and the Lakeside, each opened on its own and captured over the control map's bounds at one screen pixel per art pixel at a fixed time of 1.5 s, render identically in both looks to the committed shader (all six captures). The shader compile test takes 65 s against 54 s for the committed shader (the turn's loops are inlined wherever a layer's interior is drawn).
- **Place in the order: last, after the water.** The planks are level (no sink), so where they cross water nothing shows under them, no bank among it. The water goes on under the dock, so its edge does not run along the dock's sides: no foam, rim swell or bank there. They stay along the shore, which, with the dock a bridge, runs straight up to the dock's sides; on the beach side of the lake the shore faces down the screen and shows no bank anyway. The water's tones, strokes, glints and sparkles run on up to the dock's outline and shadow and animate as anywhere in the lake; the planks themselves need no time (frames per second 0).
- **Edges.** The planks' default edge, over every land material and over nothing: no rim, a dark outline (50, 35, 24) on the edge pixel, and a shadow (28, 20, 12) at 0.35 over 1.5 px; the boards are cut along the outline and bevelled to the light, so their ends along a dock's left side catch the light and along its right side fall in shade. Their corners are nearly square (2 px radii, against 14 and 11 for the other materials). Two overrides, planks over water and over the shallows: the same outline and a shadow cast on the water, (12, 30, 48) at 0.5 over 2.5 px. The other pairs a dock makes (over sand, over gravel where it meets a trail, over grass or dirt) take the default edge, since the earthy shadow reads right on all of them. Like every pair's shadow it falls on both sides of the edge; a shadow cast to the bottom right, or a face below a dock's bottom edges, would be the raised setting planned in Phase 10, and a dock running up the screen has no bottom edge over the water. In the soft look the planks keep their outline (no band) and draw no shadow, as every material there.
- **Movement.** `TerrainMovement_Default` has no rule for `Terrain_Planks`, so plank cells are walked at 10, like grass. They reach navigation through `PlanksTilemap`'s navigation source, whose priority is its place in the area's list, the last, so a plank cell over water is decided by the planks and walkable; the water beside the dock stays unwalkable, and a plank cell beside water costs the profile's edge cost (5) more, 15, which for a two-cell dock is every cell of it. Notes:

- **The meadow is built like grass and dry grass**: `Recipe_Meadow`, a weeds recipe (seed 20261024, 8 cells), draws weed clumps like the grass's and flower clusters over `Recipe_GrassGround`, the grass's ground, so away from a weed or a flower the meadow is the grass pixel for pixel. Flowers are a new setting of the weeds recipe, off by default (their random draws are made only with a flower chance, so grass, dry grass and tall grass write their textures exactly as before): at a chance a kept spot is a flower cluster instead of a weed, short stems in the weeds' stem and leaf greens, each topped by a head glyph ('o' petals, 'c' heart) in one petal and heart colour. Heads: a plus of four petals round a heart (twice as likely) and a 2 px square of petals. Colours: white (236, 234, 214) round yellow (232, 190, 64), yellow (240, 206, 74) round amber (196, 128, 40), pink (226, 138, 176) round pale pink (246, 212, 226) and violet (140, 128, 222) round pale yellow (236, 224, 150).
- **Reading as a meadow, not grass with noise, dry grass or crops.** A cluster takes its colour from slow colour waves at its spot (their middle half cut into four even bands, so every colour gets its share; one cluster in ten takes any colour), so neighbouring flowers share a colour and the colours lie in drifts a few cells across. The flower chance also rises and falls with the weeds' density waves (`flowerDrift`), so the drifts are thick in places and give way to plain grass with weeds in others. Spots are dense (5 per cell side, kept at 0.6 plus the density waves at 0.45; three in four kept spots flowers, plus the drift at 0.3) and clusters small (1 to 3 stems 2 to 6 px tall within 2 px of the spot, curving up to a pixel), about 6 heads per cell on average (400 over the texture's 64 cells), more where a drift is thick. Every look stays green underneath (no straw, no tint), with no rows or regular spacing, so it reads neither as dry grass nor as a crop. Rejected on the way: clusters of 2 to 5 and then 4 to 10 stems spread over up to 6 px. A box holds one cluster and boxes may not touch or leave their cell column, so wide clusters found few places: at 2.6 spots per cell side the flowers stood in a sparse lattice of bunches, a regular pattern of specks, and with 4 to 10 stems their heads merged into smears and fewer fitted still.
- **What sways.** A cluster is a weed's box: its rows lean by their weight, which rises along the stems and reaches its top at the lowest head, so the stems bend and every head moves whole, by up to the grass's 2 px in the grass's wind (8 frames per second, 2.5 s, gusts 12 cells long), and the flowers and the grass around them sway together. The meadow's and tall grass's clumps lean whole (below).

- **Tall grass is built like grass too, on a ground of its own**: `Recipe_TallGrassGround` (a grass recipe, seed 20261026, 8 cells, writing no material) is a dense hatch of 4 to 7 px blades (nine glyphs, 8 spots per cell side at 0.95) in (58, 116, 36) with tips (104, 164, 58) on a dark ground (30, 80, 26), colour patches at 0.5 from (26, 72, 26) to (44, 96, 28); `Recipe_TallGrass` (a weeds recipe, seed 20261025, 8 cells) draws clumps of 5 to 8 blades 13 to 21 px tall over it (3 spots per cell side at 0.9, feet 4 px apart, curving up to 3 px, seed heads at 0.15), stem (34, 82, 22), leaves (62, 122, 36) and (96, 158, 52), tips (150, 194, 92), shadow (24, 64, 20). ### Phase 11: shader and renderer review

`TerrainBlend.hlsl` has grown phase by phase into one 1,180-line file that every ground pixel runs through: the control map and layer masks, bridges and layers that turn to their runs, the crisp and soft shape distances, pair weights and edge settings, rims, tufts, chips and cut stones, glints, sparkles and rim swell, swaying clumps and their border checks, sunken banks, seamless edges, the composite and the debug view, about 45 functions with the two looks interleaved through `#ifdef _TERRAIN_SOFT`. Each phase added a material setting and a branch on a lookup texel, so every variant compiles every feature (the compile test takes 69 s) and every pixel checks features its area may not use. The lookup texture's layout is kept in step by hand: `TerrainBlendLut`'s column constants and the shader's `#define`s are two copies of the same numbers, row types reuse the same columns for other values, and the first columns of each row are positional. `TerrainBlendRenderer` (1,125 lines) builds the textures and chunks, follows tile changes and undo, drives brush previews, checks navigation priorities and serves the debug and probe seams; `TerrainMaterial` carries some thirty settings in one flat list. Before more effects arrive (snow's sparkles, the ocean, lava, raised ground) the design should be reviewed and, where it pays, split. This phase can run before Phases 7 to 10, whatever its number.

- **Decisions** (approved after review, with the sway header in place of the grouping; carried out one step at a time below):
  - *A file split by concern: done.* `TerrainBlend.hlsl` keeps `TerrainBlend_float` and `TerrainBlend_half` and includes eleven files: Inputs, Shape, Runs, Edges, Cells, Animation, Sway, Banks, Interior, Layer and Debug (see Architecture.md). Every function's text is unchanged (a script cut the committed file at function boundaries and checked that the lines are the same, less the include guards); the order of definitions changed only between concerns. Each file includes what it uses, so it can be read alone. The graph still imports with no messages, and an edit to an included file reaches it (a deliberate error in `TerrainBlendDebug.hlsl` made `ShaderUtil.ShaderHasError` true). The renders, debug views and blob checks of the three areas and the test scene are byte for byte the baseline's (56 files), and the compile test takes 67.2 and 67.4 s.
  - *The looks as separate files: yes.* Twelve places choose a look through `#ifdef _TERRAIN_SOFT`, seven of them in the middle of a function and two inside a loop (`TBGetEdge`, `TBRamp`), so each of those functions reads as two. The plan: `TerrainBlendCrisp.hlsl` and `TerrainBlendSoft.hlsl`, one included in place of the other by the keyword, each defining the same small set of look functions (the distance terms and a layer's distance, the outward direction, the direction banks and tufts follow, one pair's part of the edge settings and of the rim, one pair's part of what a chip's centre sees, a chip's nearest depth, `TBOpaqueInside`), and `TerrainBlendLayerCrisp.hlsl` and `TerrainBlendLayerSoft.hlsl` holding each look's `TBLayer`, which needs the interior, which needs the look functions. `TBDepthAt` moves to the soft file, its only user. Shared code then holds no `#ifdef` for the look. The risk is that a loop body moved into a function compiles to other instructions; the captures check it, and a difference would be fixed, never accepted.
  - *Features compiled out per area: no.* Compiling out what the Clearing does not use gained nothing measurable (above), because the run-time branches are uniform per layer. The variants would cost a lot: the runtime material is made in code, so the keywords would have to be `multi_compile_local` (a `shader_feature` is stripped from builds, as Phase 2 of TerrainBlending.md found for `_TERRAIN_SOFT`), and each keyword doubles every variant of the shader in every build: three keywords (water: glints, swell and banks; planks: turning and bridges; sway) make eight times today's variants, one per feature (nine) 512 times, and the compile test, which compiles every keyword combination it knows, would grow in step (about 8 x 67 s for three). The run-time branches stay.
  - *One source of truth for the lookup layout: yes, checked rather than generated.* A new `TerrainBlendLut.hlsl` holds named columns per row type (`TB_LAYER_SHAPE_COLUMN` to `TB_LAYER_SWAY_COLUMN`, `TB_PAIR_SHADOW_COLUMN` to `TB_PAIR_RAMP_COLUMN`, `TB_RAMP_TEXELS`, `TB_RAMP_STEP`) and the row functions (`TBLayerRow`, `TBFirstPairRow`), and every literal column in the HLSL is replaced by its name; `TerrainBlendLut`'s constants are renamed to match (`LayerShapeColumn` to `PairRampColumn`; only `TerrainBlendLut` and its tests use them) and every literal column in `BuildTexels` replaced too. A test in `TerrainBlendLutTests` reads the HLSL file's `#define`s and checks that each constant of `TerrainBlendLut` has its define with the same value, and the other way round. Generating the HLSL from the C# would need an editor tool and a generated file that can still be edited by hand; a failing test catches the same drift with nothing to run. Macros and a row function the compiler inlines leave the compiled code as it is.
  - *The renderer split: in part.* Out of the renderer go the chunks (a plain C# `TerrainChunkSet` that creates, fits, removes and destroys the chunk quads, about 150 lines, testable on its own), the checks (a static `TerrainBlendChecks`, about 150 lines) and the editor rebuilds (an editor-only plain C# class that remembers what a build read, follows the style's and the materials' `Validated` events and schedules the rebuild, about 150 lines, in the runtime assembly under `#if UNITY_EDITOR`, since the renderer calls it). The navigation rules stay on the renderer: they are its public API, called by four other types. Following tile changes, previews and the seams stay too: each is small and tied to the renderer's lifecycle, and moving them would move the tests' seams for little gain. The risk is the order of enabling, disabling, undo and scheduling; the renderer tests cover it.
  - *`TerrainMaterial`'s settings grouped into serializable classes: no.* The inspector already groups them under headers, so only the C# path to a setting would change. `FormerlySerializedAs` cannot move a field into a nested class, so it needs a migration through the editor (keep the old fields, copy them with `SerializedObject`, save the thirteen material assets, remove the old fields, save again): every material asset rewritten, and about fifty serialized property paths in `TerrainMaterialWriter` and the tests renamed, for no change in behaviour. Instead, a `[Header("Sway")]` above the sway settings, which today sit under Animation: an inspector change only, touching no serialized data.
  - *Not in the list, done after review (see below):* the interior is inlined twice (the interior and a seamless pair's edge pixel are exclusive branches of `TBLayer`, both calling `TBInterior` at the depth `max(-d, 0)`), and that second copy is about a third of the crisp compile time. Calling it once changes the shape of `TBLayer`'s branches, so it was left for a decision.
- **Bugs found, then fixed** (after review, before the steps below):
  - *A layer under a bridge drew its shadow and tufts past the bridge where their edges coincide.* `TBVisible` hides a layer where the next layer up's edge lies within the pair margin, which works because a layer's shape counts every layer above it; but it does not count a bridge's cells (`TBCounted`), so where a bridge and a layer painted under it end on the same line, the lower layer was not hidden and drew its own edge, shadow and tufts beneath the bridge's. In the test scene the grass under a plank strip reaching the map's edge showed its fringe's tufts below the planks, as grass blobs in the debug view (all fourteen in crisp, ten in soft). Hiding such a layer as `TBVisible` hides any other was tried first: it also hid the edge pixels of the trail's gravel where its rounded tip meets the Lakeside dock's foot, which then showed the sand under the gravel's corners as two blobs of 2 and 4 px. The fix keeps that layer's edge pixel and what lies inside it, which fill the bridge's corners, and drops only its shadow and its tufts: `TBBridgesAt` finds, once per pixel and only in an area that has a bridge, the bridge layers covering the corner patch, and where one of them lies above the layer over m with its edge within the pair margin of m's (`TBNearBridgeEdge`), the composite draws nothing of m outside its edge and gives it no tufts. The test scene's grass blobs are gone in both looks, the Lakeside changes in 8 pixels of the gravel's shadow under the dock's foot in crisp (none in soft, which draws no shadow; its blob checks as before), and the Clearing and the Village Forest, which have no bridge, render byte for byte as before. A first version looked for bridges on every layer of every pixel and drew the Lakeside about 0.3 ms slower at 8K; looking only where a bridge covers the patch brought it back within the noise (crisp 2.88 / 4.97 / 1.04, soft 3.04 / 5.37 / 1.09 ms). The compile test takes 68.7 and 68.8 s, against 67.2 before (about 2 % more, the cost of the new check; it is the baseline for the steps that follow). A renderer test covers it: a bridge column and the ground under it both ending at the map's edge, with a layer between them, leave nothing below the bridge while the ground's shadow shows beside it (the test fails without the fix). These captures are the baseline for the steps that follow.
  - *`UpdateInfo` handed the shader the serialized layer count, not the built one.* Between an inspector change to the number of layers and the scheduled rebuild, `SetDebugView` or `SetFixedTime` gave the shader a count that did not match the lookup texture it reads. It now hands it the count the renderer was built with; a renderer test adds a layer through a serialized object and checks the count before and after the rebuild. No pixel changes.
  - *Stale wording*: `TerrainMaterial`'s summary and its sway tooltip named weeds, merged into grass in Phase 3, and `TerrainStyle`'s seamless edge gave weeds over grass as its example; they now name the grass and the meadow over grass, and so does the sway file's comment.
- **The looks, separated.** `TerrainBlendLook.hlsl` includes `TerrainBlendCrisp.hlsl` or `TerrainBlendSoft.hlsl` by the keyword, and `TerrainBlendLayer.hlsl` includes `TerrainBlendLayerCrisp.hlsl` or `TerrainBlendLayerSoft.hlsl`; no other file names `_TERRAIN_SOFT`. Each look file defines the same functions: the distance terms and a layer's distance, the outward direction, the direction banks and tufts follow (`TBEdgeDirection`), one pair's look-specific part of the edge settings and of the rim (`TBAddPairEdge`, `TBRampTexel`), one pair's part of what a chip's centre sees (`TBAddCentrePair`), what else a centre needs (`TBCentreOutward`), a chip's nearest depth (`TBChipNearest`) and `TBOpaqueInside`; the crisp file also holds `TBGradient`, the soft one `TBCellHeights`, `TBSoftDistance` and `TBDepthAt`, their only users. The distances, `TBVisible` and the bridge checks moved from Shape to a new `TerrainBlendCoverage.hlsl`, after the look, and `TBEdge` and `TBCentre` to Inputs, since the look files fill them. The three areas and the test scene render byte for byte as before (56 files). The compiled fragment code is all but the same: in Sprite Lit, crisp has the same instructions as before and soft one more `mov`, a few dwords' difference in register allocation. Timing it on this machine needed care: a remote desktop streaming in the background moved the compile test between 68 and 81 s and frames by up to 20 % from one run to the next, so the step was timed against the commit before it alternately, with the editor reimporting between runs. Sprite Lit's four fragment variants took 45.7 and 49.0 s against 47.8 and 46.9 s (the compile test 70.5 and 70.6 s against 68.9 s, run apart); the Lakeside at 7680 x 4320 zoom 3, with the chunks hidden taken off, crisp 4.61 and 4.77 ms against 4.75, soft 5.74 and 5.13 ms against 5.19. Neither is slower beyond the noise.
- **A renderer test that retried nothing.** The renderer tests that read rendered pixels wait up to 30 editor updates for something to be drawn, since the first render after the terrain shader is imported draws nothing. Five of them waited on the pixel's alpha, but the probe's camera clears to opaque black, so they stopped after the first update whatever it showed, and the first of them in a run right after a shader edit failed (`ABridge_LeavesTheLayersUnderItTheirOwnEdges`, twice in this phase). They now wait on the pixel's colour (`IsDrawn`).
- **The lookup texture's layout, named once and checked.** `TerrainBlendLut.hlsl` holds a `#define` per column of each row type (`TB_SHARED_COLUMN`, `TB_LAYER_SHAPE_COLUMN` to `TB_LAYER_SWAY_COLUMN`, `TB_PAIR_SHADOW_COLUMN` to `TB_PAIR_RAMP_COLUMN`), the shared row, `TB_RAMP_TEXELS`, `TB_RAMP_STEP` and `TB_WIDTH`, and the inputs file the row functions `TBLayerRow` and `TBFirstPairRow`; every lookup read in the HLSL names its column and row through them, and the five copies of the first pair row's formula became one. `TerrainBlendLut`'s constants carry the same names (the old `AnimationColumn` and the like, and the literal columns 0 to 4 in `BuildTexels` and `WriteEdge`, renamed or replaced; only `TerrainBlendLut` and its tests used them), and `TerrainBlendLutTests.TheShadersLayoutDefines_MatchTheConstants` reads the HLSL file and fails on a constant without its define, a different value or a define that is no constant (checked by setting `TB_WIDTH` to 38). The renders are byte for byte the same, and the compiled Sprite Lit fragment code of both looks is byte for byte the previous step's, so neither compile time nor frames can have changed.
- **The renderer, split in part.** `TerrainBlendRenderer` went from 1,125 lines to 734: the chunks moved to `TerrainChunkSet` (plain C#, with a test of its own, `TerrainChunkSetTests`), the build's checks to the static `TerrainBlendChecks`, and the editor's rebuild decisions (what the last build read, following the style's and materials' `Validated` events, the scheduled rebuild) to the editor-only `TerrainBlendRebuilds`. The renderer keeps the layers and their navigation rules (public, used by its inspector, the navigation source's inspector, the scene writer and the brush), the build, following tile changes and undo, previews and the seams, which keep their names, so no test or tool changed. The renderer, brush and chunk tests pass, the renders are byte for byte the same, and a full rebuild of the Lakeside takes 12.8 to 17.4 ms against 16.3 to 18.4 ms for the renderer before the split, timed alternately (the noise of this machine; 11.3 ms in the baseline).

- **At the end.** The three areas and the test scene render byte for byte as the baseline after the bridge fix (56 files), as they did after every step; the full EditMode suite passes (731, 5 explicit benchmarks skipped). The Lakeside, timed alternately against the shader as it was before this phase (d1296ba), at 7680 x 4320 zoom 2 / zoom 3 / 1920 x 1080 zoom 3: crisp 2.80 / 4.90 / 1.05 ms against 2.70 to 2.77 / 4.98 to 5.07 / 1.04 to 1.21, soft 3.11 / 5.62 / 1.12 against 3.36 / 5.76 to 5.83 / 1.25: no frame slower beyond the noise.
- **The interior worked out once, after review.** `TBLayer` called `TBInterior` from two exclusive branches, the edge pixel along seamless pairs (`TBSeamlessEdge`) and the inside (`TBInside`), both at the depth `max(-d, 0)`, so FXC inlined the whole interior, chips, stones, sway and clump checks included, twice in each look. `TBLayerInterior` now works it out once per layer, before the branches, and only where one of them uses it: on the edge pixel of a seamless pair, or inside below a sunken layer's bank, whose height it works out first (`TBBankHeight`, which `TBInside` used to call itself); `TBSeamlessEdge` and `TBInside` take the colour it returns. The renders are byte for byte the same (56 files). ## Testing

Each phase adds the tests the existing materials have: the recipe's determinism, PNGs and look (`TerrainMaterialRecipeTests`), the lookup texture's new settings (`TerrainBlendLutTests`), the tile and palette (`TerrainTileTests`), the generators' layouts over many seeds (`AreaGenerationTests`), and the template (`AreaTemplateTests`). ## Open questions

- **R16 or RG8: R16** (decided in Phase 1). Unity lists `R16` for every desktop platform we build for, D3D11 and D3D12 require it and desktop Vulkan drivers have it; the renderer refuses to draw on a device without it. `RG8` stays the fallback if a target ever lacks it. See Phase 1's notes.
- **Texture memory at 16 layers.** Every slice of an area's arrays is as large as its largest material's textures (512 px since mud and sand repeat over 16 cells).
